# Pizza Logs 1.0.0 release contract

Author: Neil Mitchell

Last modified by: Neil Mitchell

Date: 2026-09-06

## Product scope

Version 1.0.0 marks the stable canonical Pizza Logs product for Warmane/WotLK 3.3.5a
combat logs. It includes bounded uploads, dated raid reports and encounter
breakdowns, player histories and comparisons, leaderboards, roster/gear lookups,
and private MFA administration. The [README](../../README.md#public-routes) lists
the public pages; the [surface inventory](../architecture/surface-inventory.md)
describes application, parser and administrative boundaries.

The product remains a continuously deployed personal guild site. Tagged releases
identify reviewed snapshots of that product, not separate supported hosting tiers.
The [changelog](../../CHANGELOG.md#100---2026-09-06) records this release's changes;
the existing 0.1.1 release remains the preceding snapshot.

## Compatibility commitments

- **Report links:** saved public report links remain usable through their canonical
  route or a compatibility redirect. The [canonical URL decision](../adr/0003-canonical-public-report-urls.md)
  defines report identities and dated session URLs. A presentation change must not
  silently give an existing link a different report identity.
- **Uploads:** the supported first-party workflow is the
  [bounded UUID streaming protocol](../archive-upload-protocol.md). Its documented
  progress, completion, validation and duplicate-report meanings remain the contract.
  A quick result is a preview, not a saved report. Deliberately replacing this
  workflow requires documented client migration and recovery behavior. Internal
  parser, admin and diagnostic endpoints are not a newly promised general-purpose API.
- **Metrics:** the [parser contract](../parser-contract.md) remains authoritative.
  Headline damage uses reported amounts; effective healing excludes overhealing;
  absorbs remain a separate stored primitive; heuristic encounter boundaries and
  evidence-based attribution remain required. An explicitly named analytical view
  may combine primitives without redefining the stored values.
- **Correctness fixes:** a fix that restores the documented contract can change
  values on newly parsed uploads. It requires focused regression evidence, the
  applicable parser version/provenance update and release notes. A prior defect is
  not a compatibility promise. Changing a primitive's intended meaning requires an
  explicit contract and provenance/schema decision, not a silent display change.
- **Stored reports:** releases do not silently relabel or recalculate historical
  results. Existing completed duplicates return their stored report. Correcting
  historical values requires separately reviewed recovery or reprocessing with the
  original log and a verified backup.

Product version `1.0.0`, parser version `1.1.1`, metric schema `1` and analytical
profile `canonical-v1` are independent identifiers. This release changes the
product version and branding; it adds no parser behavior change, database migration
or historical analytics recalculation relative to 0.1.1.

## Brand and browsing behavior

The approved Pizza Warriors crest replaces the geometric gold mark across the
44-pixel navigation logo, optional guild intro, browser and home-screen icons,
guild-roster loading artwork, upload notification icon, URL-share artwork, README and
repository social-preview artwork. The gold/navy palette and recognizable Pizza
Logs wordmark remain. Install/startup icons serve the platform's launch surfaces;
the existing guild-roster loading fallback represents actual work and keeps its
skeleton without introducing an artificial delay or a new root loading boundary.

The guild cinematic stays optional, with its close control, focus restoration,
sound controls and reduced-motion behavior. Its source media is not replaced by
the branding update. See the [intro behavior](../intro-animation.md) and
[asset provenance register](../security/asset-provenance.md).

## Accepted operating boundaries

- [Issue 73](https://github.com/CRSD-Lau/Pizza-Logs/issues/73) remains open because
  full representative UwU parity is unproven. Configured boss definitions do not
  prove every raid, mode, class or mechanic combination. The
  [reference evidence](../uwu-analytics-parity.md) distinguishes canonical defects
  from unresolved attribution, analytical-definition and comparison differences.
- Interrupted uploads require reupload under the accepted
  [streaming recovery decision](../adr/0004-durable-upload-boundary.md). Progress is
  process-local, raw logs are not retained as a recovery service, and this release
  adds no durable queue or resumable processing.
- [Issue 74](https://github.com/CRSD-Lau/Pizza-Logs/issues/74) remains open under the
  owner's Hobby-plan decision. Logical restoration evidence does not demonstrate
  provider-native scheduled recovery, PITR or an incident RPO/RTO. No paid backup
  alternative, infrastructure upgrade or enterprise availability promise is part
  of 1.0.0. See the [service objectives](../operations/service-objectives.md).
- [Administrator acceptance](../operations/admin-access.md#deployment-and-acceptance)
  records production enrollment, MFA access and current-device sign-out behavior.
  Together with the accepted reupload decision, it resolves the current operating
  scope of [issue 75](https://github.com/CRSD-Lau/Pizza-Logs/issues/75). It does not
  establish distributed admission, multi-region availability or provider recovery.

These boundaries remain visible quality and operating decisions. The stable
version number neither closes issues 73/74 nor claims complete reference parity,
measured service-level attainment or a security certification.

## Publication and rollout gates

This document defines release contents and requirements; it does not assert that
the tag has been published or that a particular revision is running in production.

1. Review the complete final diff and pass `npm run check:pr`. The final PR revision
   must pass all required hosted checks, including `test-build`, dependency review
   and both CodeQL language checks. Retain existing parser, database, runtime-image
   security and integrated browser gates; do not suppress failures for a brand release.
2. Verify the crest on desktop/mobile navigation, guild-roster loading and optional intro
   states, reduced motion, browser/install icons and upload notifications. Check
   readable wordmarks, focus controls, image dimensions, overflow and layout shift.
3. Verify generated metadata and directly served social/icon assets on home and
   representative report URLs. Read back the actual GitHub social-preview setting;
   committing the image alone does not update that repository setting. Existing
   browser, installed-app and social-client caches can retain earlier artwork.
4. Merge through the protected PR workflow, then verify both Railway services,
   dependency readiness, `npm run smoke:production` and representative read-only
   desktop/mobile pages against the merged revision. Follow the
   [Railway runbook](../operations/railway.md); do not change production variables
   as part of the branding release.
5. Publish `v1.0.0` at the verified merged commit and attach release notes describing
   these changes and limits. Preserve `v0.1.1` and its changelog history. Record the
   actual release, hosted checks and deployment evidence in the PR/release record.
