# Streamed Archive Upload Protocol

The primary browser path sends one raw request. It does not split uploads into
small sequential request/response chunks and does not assemble an archive in
application memory.

## Request

```http
POST /api/upload?filename=raid.zip&fileSize=31621979&uploaderName=Name
Content-Type: application/octet-stream
X-Upload-ID: <lowercase UUIDv4 generated by crypto.randomUUID()>
X-Filename: raid.zip

<raw file bytes>
```

Next.js forwards `req.body` directly to the parser endpoint:

```http
POST /uploads/<upload-id>/stream
Content-Type: application/octet-stream
X-Filename: raid.zip
```

The parser writes `<upload-id>.part` while incrementally calculating SHA-256,
flushes and fsyncs it, then atomically renames it to `<upload-id>.upload` after
the final byte. Uploads are keyed only by UUID, never client IP. Stale `.part`
and `.upload` files are removed after one hour when upload cleanup runs.

## States and results

The SSE response exposes these states:

```text
uploading -> validating -> classifying -> quick-result-ready
          -> full-processing -> complete | error
```

The browser knows the upload ID before transfer begins. The response also sets
`X-Upload-ID`. Current state is available through
`GET /api/upload/status/<upload-id>` while the parser's ephemeral state remains
within its one-hour retention window.

`quick-result` contains only segmented attempts and detector results. It is sent
before full DPS/HPS aggregation, report persistence, rankings, and milestones.
Full parsing runs afterward on a bounded worker pool; Next.js then uses the same
validated parser payload and database persistence path as the legacy endpoint.

Timing fields are separate:

- `networkUploadMs`: server receive time through the final byte
- `archiveValidationMs`: format and security validation
- `quickClassificationMs`: difficulty-only streaming scan
- `finalByteToQuickResultMs`: validation plus quick classification and handoff
- `fullProcessingMs`: full Pizza Logs parser aggregation

## Server controls

Defaults are configurable with environment variables:

| Control | Default | Environment variable |
|---|---:|---|
| Compressed bytes | 100 MiB | `UPLOAD_MAX_COMPRESSED_BYTES` |
| Selected/total uncompressed bytes | 1 GiB | `UPLOAD_MAX_UNCOMPRESSED_BYTES` |
| Archive files | 32 | `UPLOAD_MAX_ARCHIVE_MEMBERS` |
| Compression ratio | 200:1 | `UPLOAD_MAX_COMPRESSION_RATIO` |
| Receive timeout | 300 seconds | `UPLOAD_RECEIVE_TIMEOUT_SECONDS` |
| Full processing timeout | 240 seconds | `UPLOAD_PROCESSING_TIMEOUT_SECONDS` |
| Concurrent uploads | 4 | `UPLOAD_CONCURRENCY` |
| Quick workers | 2 | `QUICK_CLASSIFICATION_WORKERS` |
| Full workers | 2 | `FULL_PROCESSING_WORKERS` |
| Abandoned-file retention | 1 hour | `UPLOAD_ABANDONED_SECONDS` |

Accepted formats are `.txt`, `.log`, and `.zip`, case-insensitively. ZIP files
must have valid magic bytes and contain a usable `.txt` combat-log member.
Validation rejects encrypted members, symlinks, unsafe paths, nested archives,
too many members, excessive compressed or uncompressed size, and excessive
per-member or total compression ratios. Members are streamed with `ZipFile.open`;
archive paths are never extracted to the filesystem.

The old multipart `POST /parse-stream` parser endpoint remains available for
plain `.txt` and `.log` compatibility clients.

## Benchmark

Run from `parser/`:

```powershell
.venv\Scripts\python.exe benchmarks\benchmark_archive_upload.py --target-mib 30
```

Measured on Neil's local Windows development machine on 2026-08-10:

| Metric | Legacy baseline | Streamed archive path |
|---|---:|---:|
| Fixture | 30 MiB plain synthetic | 31,621,979-byte ZIP / 93,532,446 bytes uncompressed |
| Upload/receive | 34 ms | 35.92 ms |
| Archive validation | N/A | 8.80 ms |
| Final byte to quick result | No quick result | 1,926.60 ms |
| Full processing | 28,242 ms to legacy done | 5,158.69 ms |
| Peak memory | 268.5 MiB Python allocations | 61.81 MiB working set, +8.20 MiB |

The new representative fixture used 103 bounded attempts, DEFLATE compression at
2.96:1, and the actual raw upload endpoint. The local in-process upload feed
isolates server work from Internet transfer time; real network duration varies
and is intentionally reported separately. The quick result met the two-second
target by 73.40 ms. Heuristic logs without encounter markers use the robust CSV
segmentation fallback and may take longer on the same compressed size.
